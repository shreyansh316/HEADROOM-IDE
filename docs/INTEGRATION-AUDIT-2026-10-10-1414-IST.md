## Source facts and current ownership

### HEADROOM IDE

- `src/main/` is the Electron composition root and native-service boundary. It creates workspace, Git, terminal, language, debugger, extension, account, gateway, and workforce services and exposes them through `src/main/preload.js` IPC namespaces.
- `src/renderer/` is a plain JavaScript/DOM UI with CodeMirror 6. The renderer bundle is built by `esbuild.config.js`; no React, Next.js, or Tailwind runtime is present or needed for this native app.
- `src/main/services/gateway/` contains the IDE's multi-provider gateway (OpenAI, Anthropic, Gemini, compatible endpoint, and mock adapter), model routing, resilience, usage accounting, HTTP loopback server, and credential manager. The server is configured for `127.0.0.1:41400`.
- `src/integration/headroom/headroomEngine.cjs` is generated by `scripts/build-engine-bridge.js` from a hardcoded external `D:/codex room/headroom/src` path. The bridge bundles lower-layer HEADROOM exports and externalizes `better-sqlite3` and `vscode`.
- The existing local `HeadroomEngineAdapter` consumes HEADROOM domain/storage exports, but also owns an IDE-specific `plans`/`ide_tasks` schema, heuristic task decomposition, in-memory fallback, and manual execution logic. Its `executeTask` can execute an IPC-supplied command with `child_process.exec`, can synthesize a placeholder diff, and marks tasks complete with fabricated verification text. This is not evidence of a real HEADROOM mission runtime and conflicts with the existing task-tool authorization boundary.
- `src/main/services/gateway/CredentialManager.js` currently reads provider keys from environment variables and stores them as plaintext JSON. The `0600` file mode does not provide encryption on Windows. This does not meet the brief's secure-storage requirement.
- The main and preload processes already set `contextIsolation: true`, `nodeIntegration: false`, and `webSecurity: true`. The exposed APIs are broad; handler validation and sender/origin authorization require a focused audit before claiming the IPC boundary is secure.
- The IDE's existing feature plan is exactly 50 phases and HR-001 through HR-350. `FEATURE_REGISTRY.md` has 350 IDs, but HR-071 onward uses generic “Subsystem Capability N” names and no per-entry acceptance-criteria column. `IMPLEMENTATION_STATE.json` and `ROADMAP.md` contain status claims that need evidence reconciliation. Preserve all IDs and phase count; do not mark work verified based on build-only evidence.

### HEADROOM engine

- `src/domain/`, `src/application/`, `src/storage/`, `src/infrastructure/`, `src/agents/`, and `src/shared/` contain the reusable task, workforce, persistence, permission, provider-port, scheduler, recovery, verification, and redaction layers.
- `src/extension.js` and much of `src/core/` are VS Code host integration (commands, views, panels, configuration, secrets, workspace APIs). They must not be loaded into the desktop runtime. Keep them in the source repository; adapt their host-facing responsibilities through IDE main-process ports.
- The engine package has one runtime dependency, `better-sqlite3`. Gemini provider code uses a credential-store port; engine workflows otherwise use injected application ports. Existing HEADROOM includes transactional schema migrations, persisted task/agent repositories, task-scoped tools, authorized agent runtime, execution queue/scheduler, recovery, usage, and verification contracts.
- HEADROOM already has an Agency integration record and source inventory. It documents six re-engineered shared skills and an 80-position native catalog (4 offices, 20 departments, 4 positions per department), while keeping imported personas reference-only. Do not create another scheduler or duplicate these controls.

### Agency Agents

- `divisions.json` is the source of truth for 18 profile divisions. Counting Markdown files with agent front matter in those canonical directories found 282 profiles.
- The repository describes the profiles as prompt/persona definitions and provides installer/converter scripts for external agent products. There is no `main.py`, persistent orchestrator, Python worker protocol, Python package/dependency manifest, or execution scheduler. Four Python scripts are utilities for Hermes plugin generation/checks, not a workforce runtime.
- Preserve `LICENSE`, `divisions.json`, profile names/content, and source attribution. `integrations/` contains generated target-tool conversions; `strategy/` is playbooks/runbooks, and `examples/` and `scripts/` are tooling/examples. These are not source profile divisions and should not become runtime agents.

## Dependency and data-flow map

```text
IDE renderer (DOM + CodeMirror)
    -> narrow preload API (contextBridge)
    -> Electron main process and native services
        -> WorkspaceService / GitService / TerminalService / language tools
        -> one IDE GatewayService for provider routing, credentials, usage, and HTTP
        -> HEADROOM application/domain/storage layer via a desktop composition adapter
            -> persisted hierarchy, tasks, approvals, scoped tools, scheduler, recovery
            -> Agency profile catalog as bounded role guidance only
```

The Agency profile corpus is data, not a process. Do not add a Python worker or a second workforce loop unless a later audit uncovers an actual compatible runtime. Keep model/provider calls on the single IDE gateway and adapt the engine's provider port to it. Keep task records and execution ownership in HEADROOM repositories and use cases; do not add another task database/table set.

## Migration plan

1. **Preserve and manifest.** Retain this audit and timestamped manifest. Before editing any existing destination file, create a recoverable byte-for-byte backup under a timestamped integration backup directory and record its hash. New, non-overlapping integration directories need no replacement backup.
2. **Vendor only reusable engine sources.** Add the lower-layer HEADROOM source required by the existing bridge to `core/headroom/` (domain, application, storage, infrastructure, agents, shared, constants, and required pure helpers), with upstream HEADROOM license/provenance. Exclude the VS Code extension host, VS Code UI, tests, caches, environment files, node_modules, and release artifacts. Point the IDE bridge build at this bundled source so packaging does not require an absolute sibling checkout. Keep the IDE lockfile authoritative and verify native dependency compatibility rather than merging lockfiles.
3. **Consolidate mission ownership.** Replace the custom IDE plan/task lifecycle with a composition adapter over HEADROOM use cases/repositories. Preserve existing `.headroom/headroom.sqlite` and its schema; use transactional versioned migrations only if a demonstrated engine integration requires them. Do not drop custom tables or rewrite existing user database data during this integration. Remove fabricated completion/diff behavior and reject arbitrary renderer-supplied task commands; route task operations through HEADROOM's task-scoped permissions, provider budget, scheduler, verification, cancellation, and recovery.
4. **Use one provider gateway.** Keep the IDE GatewayService as the only provider router and usage/credential owner. Adapt the HEADROOM provider port to that gateway. Replace plaintext credential persistence with Electron `safeStorage`-backed storage and a controlled, non-destructive migration path; never return raw keys to the renderer or copy `.env` values into the IDE.
5. **Adapt Agency definitions, not its installer/runtime.** Add only the 18 canonical profile directories, 282 frontmatter profiles, division registry, MIT license, and attribution under a dedicated `core/agency-agents/` resource path. Parse and validate profile metadata in the main process, expose bounded metadata through IPC, and make profile guidance an explicit persisted-agent selection. Treat imported profile text as untrusted guidance; it must not grant tools, workspace scope, provider credentials, approvals, or commands. Preserve existing six shared skills and 80-position catalog.
6. **Harden and bind the native interface.** Validate IPC sender and arguments; ensure workspace paths stay inside the selected canonical root, including symlink/Win32 aliases; keep terminal commands explicitly user-initiated and task process calls behind persisted grants. Bind real workspace/file/dirty/mission/agent/provider/usage state and represent unavailable states honestly.
7. **Verify in layers.** Run existing IDE and HEADROOM tests, focused adapter and protocol/security tests, syntax/lint/TypeScript prohibition, engine bridge build, production build, and desktop/package smoke checks where supported. A safe local mission must prove persisted submission, approval gate, authorized execution, progress, cancellation/recovery behavior, verification evidence, and reviewable diff. Never make a live provider call without configured credentials and explicit authorization. Record command exit codes and distinguish mocked tests from real provider/desktop evidence.
8. **Reconcile docs without changing plan identity.** Update architecture, migration/evidence docs and implementation ledger. Keep exactly 50 phases and HR-001–HR-350. Give existing generic registry entries meaningful criteria before treating them as authoritative; only update established entries with evidence, never invent IDs.

## Unresolved audit items before implementation claims

- The existing IDE adapter bypasses the HEADROOM application execution pipeline and fabricates task evidence; the current “end-to-end” test names do not establish a real provider-backed mission.
- IDE gateway credentials are plaintext at rest. Replace this before claiming secure credential storage.
- Full IPC sender/argument authorization and workspace path containment need focused tests and fixes before enabling agent writes or task process operations.
- The Agency source has no Git metadata, so source commit identity and upstream history cannot be recorded. The 381-file local snapshot and profile hashes should be recorded in the integration manifest.
- The feature registry contains placeholder names and lacks feature-level acceptance criteria in later phases; current phase/feature status needs reconciliation against executed evidence.
